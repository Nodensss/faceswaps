# Техническое задание: FaceSwapLocal

- Версия документа: 1.0
- Целевая платформа: Android 9 / API 28 и новее
- Тип продукта: личное полностью локальное мобильное приложение
- Основной стек: Kotlin, Jetpack Compose, coroutines, Android SDK

## 1. Инструкция исполнителю Codex

Работай в существующем репозитории автономно и используй компьютер для реальной
реализации: терминал, Android Studio, Gradle, Android SDK, эмулятор и `adb`, если
доступен подключённый телефон. Не ограничивайся планом или демонстрационными
заглушками.

Перед началом:

1. Прочитай `AGENTS.md`, этот документ и `README.md` целиком.
2. Изучи текущее состояние исходников и не переписывай уже рабочие части без причины.
3. Проверь `git status` и сохрани все пользовательские изменения.
4. Проверь наличие JDK 17, Android SDK 35 и работоспособность Gradle Wrapper.
5. Создай короткий рабочий план и выполняй его по одному проверяемому этапу.

Во время работы:

- используй терминал и Android Studio для сборки, тестирования и диагностики;
- после каждого законченного этапа запускай относящиеся к нему тесты;
- не добавляй сервер, сетевую обработку или скрытую загрузку файлов;
- не публикуй репозиторий, APK, фотографии или модели во внешних сервисах без
  отдельного указания пользователя;
- если требуется системная установка с правами администратора, сначала запроси
  разрешение; Android SDK и зависимости по возможности устанавливай в пользовательскую
  директорию;
- не называй этап готовым, пока соответствующий пользовательский сценарий не работает
  на эмуляторе или реальном устройстве;
- при блокере исчерпай безопасные локальные способы диагностики и зафиксируй точную
  причину, команду и ошибку.

Перед завершением работы обязательно выполни:

```bash
./gradlew test
./gradlew lint
./gradlew assembleDebug
```

Если подключено Android-устройство, дополнительно проверь:

```bash
adb devices
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

Устанавливать APK на телефон следует только после подтверждения пользователя либо
если он явно поручил установку в текущей задаче.

## 2. Назначение продукта

FaceSwapLocal должен качественно заменять одно или несколько лиц:

- на одной фотографии;
- на группе людей в одной фотографии;
- на видео после завершения и стабилизации фото-MVP.

Вся работа выполняется на Android-устройстве. Исходные материалы, биометрические
признаки, промежуточные кадры и готовые результаты не должны покидать устройство.

## 3. Ожидаемый конечный результат

Пользователь устанавливает APK, выбирает лица-источники и целевое фото или видео,
назначает замену для каждого найденного лица, запускает обработку, сравнивает результат
с оригиналом и сохраняет новый файл в галерею.

Приложение должно поддерживать следующие варианты:

1. Один источник → одно целевое лицо.
2. Один источник → несколько целевых лиц.
3. Несколько источников → разные лица на одной фотографии.
4. Некоторые целевые лица заменяются, остальные остаются без изменений.
5. Несколько устойчивых треков лиц в видео → независимые источники.

## 4. Исходное состояние проекта

В репозитории уже находятся:

- проект Android на Kotlin и Jetpack Compose;
- системный Photo Picker для выбора исходной и целевой фотографии;
- локальная загрузка изображений;
- bundled ML Kit Face Detection;
- обнаружение, рамки и нумерация нескольких лиц;
- базовое сопоставление целевых лиц с источниками;
- интерфейс `FaceSwapEngine`;
- доменные тесты правил сопоставления;
- Gradle Wrapper и базовый GitHub Actions workflow.

Нейросетевая замена, маска, смешивание, экспорт, пакет источников и обработка видео
пока не реализованы. Нельзя выдавать текущий `FaceSwapEngine` за работающий inference.

## 5. Обязательные ограничения

### 5.1 Приватность

- В `AndroidManifest.xml` запрещено разрешение `android.permission.INTERNET`.
- Запрещены аналитика, телеметрия, реклама, аккаунты, облачные API и crash-reporting,
  отправляющий данные наружу.
- Для выбора медиа использовать системный Photo Picker или Storage Access Framework;
  не запрашивать полный доступ к хранилищу.
- Эмбеддинги лиц по умолчанию хранить только в оперативной памяти текущей сессии.
- Не сохранять исходные изображения во внутренней базе приложения.
- Временные файлы создавать только в приватном `cacheDir`/`codeCacheDir`.
- Удалять временные данные после успеха, ошибки, отмены и при следующем запуске после
  аварийного завершения.
- Из экспортируемого файла по умолчанию удалять геолокацию и иные чувствительные EXIF-поля.
- Android backup должен оставаться отключённым.

### 5.2 Технические ограничения

- `minSdk = 28`, если документированная необходимость не требует изменения.
- UI: Kotlin + Jetpack Compose.
- Асинхронность: Kotlin coroutines и `StateFlow`.
- Длительные операции не выполнять на Main thread.
- Inference выполняется только локально через подходящий Android runtime.
- Для фото сохранять исходное разрешение результата; нейромодель может работать на
  выровненном кропе меньшего размера, который затем смешивается с оригиналом.
- Пиковое потребление памяти должно быть ограничено; нельзя держать все кадры видео
  одновременно.
- Не добавлять веса моделей в Git до документирования источника и лицензии.

### 5.3 Ответственное использование

- При первом запуске показать короткое уведомление: использовать материалы только с
  согласия изображённых людей и не выдавать обработанный материал за подлинный.
- Сохранить в метаданных результата нейтральную отметку о редактировании, когда формат
  позволяет это сделать.
- Видимый водяной знак сделать отдельной настройкой, включённой по умолчанию, с
  возможностью отключения для личного использования.

## 6. Границы версии 1.0

Входит в версию 1.0:

- фото с одной и несколькими заменами;
- локальный inference;
- просмотр, сравнение и экспорт;
- видео MP4 после готовности фото-пайплайна;
- сохранение аудиодорожки видео;
- прогресс и отмена длительной операции.

Не входит в версию 1.0:

- iOS;
- веб-версия и серверная часть;
- live face swap с камеры;
- изменение голоса или аудио;
- автоматическая публикация в соцсети;
- гарантированная обработка 4K-видео на любом устройстве;
- обучение модели на телефоне.

## 7. Функциональные требования к фотографиям

### FR-PHOTO-01. Набор лиц-источников

- Пользователь может добавить от 1 до 8 фотографий-источников.
- На каждой фотографии обнаруживаются все подходящие лица.
- Пользователь отмечает, какие обнаруженные лица добавить в набор источников.
- Каждому источнику присваивается номер, миниатюра и стабильный идентификатор сессии.
- Один и тот же источник разрешено назначать нескольким целевым лицам.
- Источник можно удалить или заменить до запуска обработки.

### FR-PHOTO-02. Целевая фотография

- Пользователь выбирает одну фотографию из системного Photo Picker.
- Поддерживаются форматы, декодируемые Android `ImageDecoder`, как минимум JPEG, PNG
  и WebP.
- EXIF-ориентация должна учитываться до детекции и обработки.
- Для очень больших файлов создаётся уменьшенный preview, но экспорт сохраняет размеры
  оригинала, если устройство способно обработать файл без риска OOM.

### FR-PHOTO-03. Обнаружение лиц

- Найти все различимые лица на источниках и цели.
- Отсортировать лица детерминированно: сверху вниз, затем слева направо.
- Показать рамку и номер каждого лица.
- Не считать порядковый номер постоянной идентичностью между разными файлами.
- Показать предупреждение для слишком маленького, размытого или сильно повёрнутого лица.
- Ошибка одного лица не должна блокировать работу с остальными лицами.

### FR-PHOTO-04. Сопоставление

- Для каждого целевого лица пользователь выбирает источник либо значение «Не менять».
- По умолчанию первое лицо-источник назначается только первому целевому лицу; остальные
  должны ожидать явного выбора либо использовать отдельно выбранную команду «Применить
  ко всем».
- Выбранные назначения должны сохраняться при повороте экрана и пересоздании Activity.
- При удалении источника связанные назначения переводятся в состояние «Не выбрано».

### FR-PHOTO-05. Настройки обработки

Обязательные настройки:

- качество: «Быстро», «Баланс», «Максимум»;
- сила сохранения идентичности;
- растушёвка границы маски;
- цветокоррекция: авто/выключено;
- восстановление деталей лица: авто/выключено;
- видимый водяной знак: включён/выключен.

Значения должны иметь безопасные рабочие defaults. Расширенные настройки не должны
мешать базовому сценарию «выбрал → назначил → обработал».

### FR-PHOTO-06. Нейросетевая замена

Для каждой пары выполнить:

1. Нормализацию ориентации исходного изображения.
2. Детекцию и получение ключевых точек.
3. Выравнивание лица в координаты, ожидаемые моделью.
4. Извлечение identity embedding источника, если это требуется выбранной моделью.
5. Генерацию заменённого лица из целевого кропа и identity embedding.
6. Обратное геометрическое преобразование в координаты целевого фото.
7. Построение маски с защитой волос, глаз, рта и областей перекрытия, насколько это
   поддерживает выбранный пайплайн.
8. Цветовое согласование с целевой сценой.
9. Мягкое смешивание с оригиналом.
10. Опциональное восстановление деталей без заметного изменения идентичности.

Обработка нескольких лиц выполняется в стабильном порядке. Маски пересекающихся лиц
не должны повреждать уже обработанные области.

### FR-PHOTO-07. Прогресс и отмена

- Показать этап, общее число лиц, текущий номер и прогресс.
- Во время обработки запретить повторный запуск той же задачи.
- Кнопка «Отмена» должна останавливать coroutine/inference на ближайшей безопасной
  границе, освобождать tensor/session resources и удалять временные файлы.
- Поворот экрана не должен перезапускать обработку.

### FR-PHOTO-08. Предпросмотр результата

- Показать результат без автоматического сохранения.
- Добавить сравнение «до/после» нажатием или ползунком.
- Разрешить вернуться к назначениям и настройкам.
- При повторной обработке корректно освободить предыдущий bitmap.

### FR-PHOTO-09. Экспорт

- Сохранить результат через `MediaStore` в коллекцию изображений.
- Формат по умолчанию: JPEG с настраиваемым качеством; PNG доступен при необходимости.
- Имя: `FaceSwapLocal_yyyyMMdd_HHmmss.ext`.
- После успеха показать миниатюру, путь/альбом и системную кнопку «Открыть».
- При ошибке удалить незавершённую запись `MediaStore`.
- Не перезаписывать исходный файл.

## 8. Функциональные требования к видео

Видео начинается только после выполнения критериев готовности фото-MVP.

### FR-VIDEO-01. Импорт и анализ

- Выбрать одно локальное видео через системный picker.
- Минимально поддержать MP4 с кодеком H.264, если он декодируется устройством.
- Прочитать длительность, разрешение, rotation metadata, FPS и наличие аудио.
- Создать лёгкий анализ кадров с регулируемым шагом и найти устойчивые face tracks.
- Показать миниатюру каждого трека и временной диапазон его присутствия.

### FR-VIDEO-02. Назначение треков

- Для каждого трека выбрать источник либо «Не менять».
- Позволить исправить ошибочно объединённые треки и объединить части одного трека.
- Не менять человека до момента уверенного сопоставления трека.
- Сохранять назначения на всём диапазоне трека.

### FR-VIDEO-03. Обработка кадров

- Декодировать кадры последовательно через Android media APIs.
- Использовать ограниченную очередь кадров, чтобы не вызвать OOM.
- Для каждого трека сглаживать landmarks, affine transform, маску и параметры цвета.
- Повторно использовать identity embedding источника.
- При временной потере лица использовать безопасный gap policy: короткий пропуск можно
  интерполировать, при долгом пропуске замену остановить до повторного уверенного захвата.
- Не генерировать лицо, если confidence ниже настроенного порога.
- Сохранять исходные размер, длительность, ориентацию и приблизительный FPS.

### FR-VIDEO-04. Временная стабильность

Результат не должен заметно мерцать между соседними кадрами. Требуется:

- стабильный ID трека;
- сглаживание геометрии и маски;
- ограничение резких изменений цвета и силы смешивания;
- детекция scene cut со сбросом временного состояния;
- отсутствие «перепрыгивания» источников между людьми при пересечении лиц.

### FR-VIDEO-05. Кодирование и аудио

- Экспорт: MP4/H.264 через `MediaCodec` и `MediaMuxer` либо другой локальный Android
  механизм с документированным обоснованием.
- Скопировать исходную аудиодорожку без модификации, когда формат совместим.
- Если аудио невозможно скопировать, до запуска экспорта предупредить пользователя.
- Не оставлять частично созданный файл после ошибки или отмены.

### FR-VIDEO-06. Фоновая работа

- Для длинной обработки использовать корректный foreground execution с уведомлением,
  прогрессом и действием «Отменить».
- После убийства процесса задача должна либо безопасно восстановиться с контрольной
  точки, либо завершиться с очисткой и понятным сообщением при следующем запуске.
- Не хранить декодированные кадры дольше необходимого.

## 10. Архитектура

Рекомендуемая структура пакетов:

```text
com.faceswaplocal.app
├── data          # decoding, MediaStore, session cleanup
├── domain        # immutable models and use cases
├── inference     # model sessions, preprocessing, postprocessing
├── media         # image/video pipelines and codecs
├── tracking      # video face tracks and temporal smoothing
├── ui            # Compose screens and view models
└── workers       # long-running local processing
```

Ключевые сущности:

- `SourceIdentity`: источник, face crop, landmarks и временный embedding.
- `TargetFace`: лицо на целевой фотографии.
- `TargetTrack`: устойчивый человек/трек в видео.
- `SwapAssignment`: nullable-связь цели с источником.
- `ProcessingSettings`: качество, mask feathering, color match, restoration.
- `ProcessingProgress`: этап, текущий элемент, общее количество, доля выполнения.
- `ProcessingResult`: URI результата и диагностические метрики без персональных данных.

Интерфейсы, которые должны отделять runtime от UI:

```kotlin
interface FaceEmbedder {
    suspend fun embed(alignedSource: Bitmap): FloatArray
}

interface FaceSwapEngine {
    suspend fun swap(request: FaceSwapRequest): Bitmap
}

interface FaceMasker {
    suspend fun createMask(face: Bitmap): Bitmap
}

interface PhotoProcessor {
    fun process(request: PhotoProcessingRequest): Flow<ProcessingEvent>
}

interface VideoProcessor {
    fun process(request: VideoProcessingRequest): Flow<ProcessingEvent>
}
```

Названия и сигнатуры можно уточнить, но:

- runtime-specific tensor/session types не должны попадать в ViewModel;
- ViewModel не должен владеть `ContentResolver`, codec session или inference session;
- bitmap/tensor lifetime должен быть явным;
- закрываемые ресурсы освобождаются через `try/finally`;
- ошибки домена должны преобразовываться в понятные сообщения UI.

## 11. Выбор и подключение модели

Codex должен сначала исследовать доступные on-device решения и выбрать пайплайн по
качеству, производительности, размеру и лицензии. Использовать первичные источники:
официальный репозиторий, model card, файл лицензии и документацию runtime.

До добавления весов создать `docs/MODEL_CARD.md` со следующими полями:

- название и версия модели;
- автор/организация;
- точный URL источника;
- URL и полный идентификатор лицензии;
- разрешено ли личное использование;
- разрешено ли распространение весов внутри APK и репозитория;
- дата проверки условий;
- SHA-256 каждого файла весов;
- размер модели;
- формат и имена входов/выходов;
- размер, нормализация и channel order входов;
- алгоритм alignment и необходимые landmarks;
- способ получения identity embedding;
- ограничения модели и известные артефакты;
- результаты benchmark на реальном Android-устройстве.

Правила:

1. Если распространение разрешено, веса можно положить в assets только после заполнения
   `MODEL_CARD.md` и `THIRD_PARTY_NOTICES.md`.
2. Если распространение запрещено или неоднозначно, не коммитить веса. Реализовать
   локальный импорт модели через системный picker либо предоставить пользователю точную
   инструкцию установки.
3. Не скачивать модель с неофициального зеркала, если существует первичный источник.
4. Проверять SHA-256 до открытия model session.
5. Не маскировать несовместимость модели заглушкой или случайным изображением.
6. Runtime выбирается после минимального benchmark. Допустимы ONNX Runtime Mobile,
   LiteRT/TFLite или другой полностью локальный Android runtime с подходящей лицензией.
7. Добавить CPU fallback. GPU/NNAPI delegate использовать только после проверки
   корректности результата и надёжного fallback.

## 12. Производительность и управление памятью

Первое реально подключённое устройство пользователя считается reference device. Codex
должен записать модель телефона, Android version, SoC, RAM и backend inference в
`docs/BENCHMARKS.md` без серийного номера и других идентификаторов.

Обязательные требования:

- приложение не падает с OOM на 12-мегапиксельном JPEG при обработке одного лица на
  reference device;
- preview декодируется отдельно от полноразмерного изображения;
- одновременно в памяти находится минимально необходимое количество полноразмерных
  bitmap;
- все inference и media операции выполняются вне Main thread;
- UI остаётся отзывчивым и позволяет отмену;
- видео использует bounded queue, рекомендуемая глубина 2–3 кадра;
- embeddings источников кешируются только на время задачи;
- после завершения память освобождается и подтверждается Android Studio Profiler либо
  повторным циклом обработки без устойчивого роста heap.

Для каждого benchmark зафиксировать:

- входное разрешение и число лиц;
- режим качества;
- backend CPU/GPU/NNAPI;
- время детекции, inference, blending и общее время;
- приблизительный peak Java/native heap;
- температуру/thermal throttling, если Android сообщает это состояние;
- визуально обнаруженные артефакты.

Производительность оценивается по реальным измерениям. Нельзя ухудшать медианное время
контрольного сценария более чем на 20% без объяснения и изменения benchmark-файла.

## 13. Обработка ошибок

Предусмотреть отдельные пользовательские сообщения для случаев:

- файл недоступен или повреждён;
- лицо не найдено;
- лицо слишком маленькое для выбранного качества;
- формат/codec не поддерживается устройством;
- модель отсутствует или не прошла проверку checksum;
- недостаточно оперативной памяти или свободного места;
- inference backend недоступен, выполнен переход на CPU;
- сохранение в MediaStore не удалось;
- пользователь отменил операцию;
- Android остановил foreground processing.

Технический stack trace не показывать в UI. В debug build разрешён локальный Logcat без
путей к пользовательским файлам, embeddings, изображений и иных персональных данных.

## 14. Тестирование

### 14.1 Unit tests

- создание и изменение `SwapAssignment`;
- удаление источника и очистка зависимых назначений;
- deterministic ordering лиц;
- преобразование координат и inverse transform;
- mask compositing и alpha boundaries;
- color normalization на синтетических массивах;
- расчёт progress;
- cleanup state machine;
- video track association на синтетических последовательностях.

### 14.2 Instrumentation tests

- восстановление UI после rotation/process recreation;
- выбор нескольких источников;
- «Не менять» для части лиц;
- отмена обработки;
- успешный экспорт через MediaStore;
- удаление незавершённого MediaStore item после ошибки;
- отсутствие сетевого разрешения в merged manifest;
- отсутствие сетевых запросов при полном пользовательском сценарии.

### 14.3 Golden/quality tests

- Использовать только синтетические либо явно лицензированные тестовые изображения.
- Не коммитить личные фотографии пользователя.
- Сценарии: фронтальное лицо, поворот, очки, борода, частичное перекрытие, несколько
  людей, разные оттенки освещения.
- Сравнивать alignment, маску и итоговый кроп с утверждёнными golden-файлами с разумным
  допуском для разных inference backends.
- Для видео добавить короткий лицензированный fixture с движением, поворотом,
  перекрытием и scene cut.

### 14.4 Ручная приёмка на устройстве

1. Чистая установка APK.
2. Запуск в авиарежиме.
3. Одиночная замена на фото.
4. Две разные замены на групповом фото.
5. Одно целевое лицо отмечено «Не менять».
6. Отмена во время обработки и проверка отсутствия временных файлов.
7. Экспорт, открытие результата из галереи и проверка размеров.
8. Повторить обработку 5 раз и проверить отсутствие заметного роста памяти.
9. После готовности видео: сохранить ролик, проверить длительность, звук, ориентацию,
   стабильность треков и отсутствие временных кадров.

## 15. Этапы реализации и Definition of Done

### Этап A. Воспроизводимая базовая сборка

Задачи:

- открыть существующий проект;
- выполнить Gradle Sync;
- исправить build/lint/test ошибки без изменения продуктовых ограничений;
- запустить приложение на эмуляторе или телефоне;
- проверить выбор фото, multi-face detection и mapping UI.

Готово, когда `test`, `lint` и `assembleDebug` проходят, а текущий сценарий работает
на устройстве.

### Этап B. Настоящая одиночная замена на фото

Задачи:

- выбрать и документировать модель;
- подключить локальный runtime;
- реализовать preprocessing, identity embedding, swap и inverse transform;
- показать настоящий результат для одной пары лиц;
- добавить CPU fallback и unit tests преобразований.

Готово, когда результат реально меняет идентичность выбранного целевого лица, сохраняет
позу/выражение цели и воспроизводится в авиарежиме. Заглушка, наложение прямоугольника
или простое копирование исходного кропа не считаются face swap.

### Этап C. Несколько источников и целей

Задачи:

- добавить пакет фотографий-источников;
- реализовать «Не менять» и «Применить ко всем»;
- обработать несколько назначений без конфликтов масок;
- сохранить UI state при rotation;
- добавить тесты invalidated assignments.

Готово, когда пользователь может назначить минимум три разных источника трём людям на
одной фотографии и оставить четвёртого без изменения.

### Этап D. Качество и экспорт фото

Задачи:

- маска, feathering, color matching и restoration;
- сравнение до/после;
- настройки качества;
- прогресс и отмена;
- экспорт через MediaStore;
- cleanup и memory profiling.

Готово, когда фото-сценарии ручной приёмки проходят, исходный файл не изменяется, а
незавершённые данные не остаются после ошибки или отмены.

### Этап E. Видео

Задачи:

- анализ видео и face tracks;
- UI назначения источников трекам;
- streaming decode/inference/encode;
- temporal smoothing и scene cut handling;
- копирование аудио;
- foreground progress/cancel/cleanup;
- короткие video fixtures и ручная приёмка.

Готово, когда короткий контрольный MP4 с несколькими людьми обрабатывается полностью
локально, сохраняет длительность и звук, а личности не перепрыгивают между треками.

### Этап F. Финальный APK

Задачи:

- полный test/lint/build;
- release minification smoke test;
- актуализировать документацию и third-party notices;
- сформировать debug APK и при наличии пользовательского keystore — подписанный release
  APK без добавления ключа или пароля в репозиторий;
- записать известные ограничения.

Готово, когда APK устанавливается на reference device и все обязательные сценарии
приёмки выполнены в авиарежиме.

## 17. Критерии окончательной приёмки

Продукт принимается, если одновременно выполнены условия:

- приложение устанавливается и запускается на Android API 28+;
- в merged manifest отсутствует `INTERNET`;
- одиночная и множественная замена являются настоящим локальным neural inference;
- пользователь может независимо назначить источник или «Не менять» каждому лицу;
- результат фото сохраняется в галерею без изменения оригинала;
- обработка отменяется без остаточных файлов;
- повторные циклы не приводят к устойчивому росту памяти;
- модель и все зависимости имеют документированные источники и лицензии;
- unit tests, lint и debug build проходят;
- приложение работает в авиарежиме;
- после реализации видео сохраняются звук, длительность, ориентация и стабильная
  привязка источников к face tracks;
- Codex передал APK, результаты проверок и честный список ограничений.
