# Известные ограничения FaceSwapLocal

Дата актуализации: 04.08.2026; состояние после контрольной точки 2 этапа E2.

- Фото-координатор поддерживает несколько независимых назначений и последовательный
  композит поверх накопленного результата. UI этапа D закрыт тестами, но полная ручная
  приёмка качества на реальной групповой фотографии ещё не выполнялась.
- BiSeNet parser-mask подключена к блендингу свапа и восстановления. На синтетических
  `pair_02` и `pair_03` она убрала переходы у волос, виска и нижней границы бороды.
  Отдельной occlusion/xseg-модели для рук, сложных перекрытий и прозрачных оправ пока
  нет; эти случаи нельзя считать закрытыми одной face-region mask.
- Цветосогласование masked RGB mean/std считает статистику по аффинной box-mask, а не
  по parser-region. На `pair_02`/`pair_03` parser покрывает лишь 53,95%/53,88% её
  веса, поэтому фон и волосы могут смещать коррекцию. После GFPGAN residual отношения
  face↔neck улучшился на `pair_02` (`3,949 → 2,504` ΔE76), но ухудшился на `pair_03`
  (`3,992 → 6,034`); менять алгоритм по синтетическим fixtures нельзя. Parser-scoped
  статистика и сохранение цветности при восстановлении требуют повторного измерения
  на разрешённом реальном фото.
- InSwapper работает на кропе 128×128. GFPGAN 1.4 уже подключён во втором проходе и
  strength `0.8` не изменил ближайший source в ArcFace-проверке; даже strength `1.0`
  сохранил ранжирование. Тем не менее резкость и identity должны быть перепроверены на
  разрешённом реальном фото и физическом reference device. UI уже позволяет включать
  GFPGAN, менять силу `0…1` и выбирать parser/box маску свапа; пресеты качества,
  identity strength, ручной feathering, color auto/off и watermark относятся к E2.
- Текущий parity-набор не содержит открытого рта, поэтому геометрия зубов в финальном
  кадре отдельно не проверена. Глаза и рот проверены на всех трёх парах.
- HyperSwap 1a 256 численно совпадает с FaceFusion, но на трёх синтетических parity-
  парах переносит identity заметно слабее InSwapper. Поэтому текущий UI-default —
  `inswapper_128_fp16`; HyperSwap остаётся основным кандидатом shortlist до проверки
  на расширенном лицензированном наборе.
- Полный FaceFusion production flow может уточнять пять точек через 68-point
  landmarker. Текущий Android pipeline использует исходные пять точек YOLO; refined
  landmarks ещё не подключены.
- Android использует closed-form least-squares affine и bilinear sampling вместо
  FaceFusion/OpenCV RANSAC и `INTER_AREA`. На текущем наборе geometry/raw/final parity
  проходит пороги, но набор сложных ракурсов и перекрытий следует расширить.
- ONNX Runtime 1.26.0 завершает процесс нативным `SIGABRT` при создании XNNPACK-
  сессии InSwapper на API 35 x86_64 AVD. Пользовательский путь закреплён на CPU;
  известные x86 ABI превентивно получают CPU fallback, а XNNPACK нельзя считать
  поддержанным до отдельной проверки на реальном ARM64-устройстве.
- В production одна BiSeNet-сессия живёт всю photo-задачу. Допустимые пиковые пары —
  BiSeNet+InSwapper в первом проходе и BiSeNet+GFPGAN во втором; InSwapper и GFPGAN
  одновременно не открываются. Суммы файлов весов этих пар — 371 313 375 и
  433 931 633 байт, но это не peak heap.
- Peak Java/native heap впервые измерены на сквозном прогоне 12 МП (AVD API 35):
  161,6 МиБ Java, 1 249,1 МиБ native, 1 294,3 МиБ total PSS при потолке кучи 512 МиБ.
  Запас до ориентира §12 (~1,5 ГБ) невелик. Thermal и пять повторных циклов на
  физическом reference device по-прежнему не выполнены: подключённого Android-телефона
  не было. Результаты API 35 AVD не являются прогнозом производительности телефона.
- Полная SHA-256-проверка модели выполняется один раз за процесс. Последующие сессии
  проверяют канонический путь в приватном `filesDir/models` и размер; после перезапуска
  процесса полное хеширование повторяется. Это осознанное отклонение по
  производительности, не отменяющее проверку при импорте и первом использовании.
- Лицензионные условия весов не дают достаточного основания для их распространения:
  модели не входят в Git/APK и импортируются пользователем локально. Детали находятся
  в `docs/MODEL_CARD.md` и `THIRD_PARTY_NOTICES.md`.
- Константа 2 560 px для целевого фото убрана: предел вычисляется `ImageMemoryBudget`
  из реальной свободной Java-кучи и доступной системной памяти. Источники остаются на
  2 560 px по длинной стороне — из них берётся только выровненный кроп, их может быть
  восемь одновременно, и все parity-фикстуры этапов B–E1 измерялись через этот предел.
- Для полноразмерного композитинга включён `android:largeHeap="true"`. Без него предел
  Java-кучи на устройстве класса 2 ГБ равен 192 МБ, и адаптивный бюджет ограничил бы
  любое фото примерно 5 МП. Это подняло потолок, но не отменило проверку: бюджет
  по-прежнему читает фактический `Runtime.maxMemory()`.
- Если памяти не хватает, цель декодируется меньше оригинала, и UI прямо сообщает об
  этом перед сохранением. Экспорт всегда равен обработанному размеру, а не размеру
  исходного файла.
- На Android 9 (API 28) экспорт требует ручного выбора папки и имени через диалог
  Storage Access Framework: отложенной `IS_PENDING`-записи в этой версии нет, а вставка
  в общую коллекцию `MediaStore` потребовала бы запрещённого §5.1 полного доступа к
  хранилищу. Путь SAF реализован и покрыт инструментальным тестом, но на реальном
  устройстве API 28 не проверялся — доступен только AVD API 35.
- Отметка о редактировании пишется платформенным `android.media.ExifInterface`
  (JPEG) и собственным `tEXt`-чанком (PNG). Форматы без такой поддержки остались бы без
  отметки; сейчас экспорт предлагает только JPEG и PNG.
- Отмена останавливает обработку на ближайшей границе `ensureActive` координатора:
  уже начатый inference одного лица доводится до конца, после чего проход
  прекращается. Мгновенного прерывания внутри нативного вызова ONNX Runtime нет.
- Этап E1 закрыт на утверждённом синтетическом parity-наборе; сравнение «До/После»
  выполнено досрочно из E2. Сам этап E2 ещё не закрыт: в контрольной точке 1 сделаны
  экспорт `MediaStore`, метаданные, водяной знак, прогресс с отменой и cleanup; в
  контрольной точке 2 — полное разрешение цели и удержание экрана. Остаются пресеты
  качества, identity strength, ручной feathering и color auto/off. Видео и
  release-оптимизация относятся к этапам F–G.
